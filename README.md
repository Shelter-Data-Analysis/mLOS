# mLOS — Length-of-Stay Analysis Tool

mLOS is an R tool that analyzes length-of-stay (LOS) in animal shelters. It compares how long animals stay in care across user-defined time periods, intake types, or animal groups, using proper survival-analysis methods (Kaplan-Meier, Cox regression, Aalen-Johansen competing risks) rather than misleading simple averages.

## Start here

If you're new to the project, read in this order:

1. **[`mlos_user_guide.md`](mlos_user_guide.md)** — start with the "For Practitioners" section at the top for a plain-language explanation of what the tool does and why (no stats background assumed). The "Technical Reference" section below it documents every output file and plot.
2. **[`mlos_math_methods.md`](mlos_math_methods.md)** — the authoritative, detailed reference for every statistical convention, estimator, and formula used. Read this if you need to interpret or reproduce results precisely, or if you're modifying the analysis code.
3. **[`tests/README_TESTS.md`](tests/README_TESTS.md)** — explains the test suite, how to run it, and the "golden file" workflow for reviewing changes to outputs. Read this before modifying any code.
4. **[`presentation_guide.md`](presentation_guide.md)** — covers the experimental Python deck builder in `mlos_review/`. The deck-builder takes some of the plots and numbers generated by the statistical analysis and bundles them into a PowerPoint slide deck.  Read this only if you want to generate slides. Its caveats are summarized under "Building a slide deck" below and stated in full there.  (The statistical results stand on their own without the deck builder.)

The `.md` files are the documentation of record. Read them in any markdown reader, Obsidian among them, or in the browser on GitHub. Word versions of the three guides are tracked here for sharing and printing, but they are rebuilt only when a release is cut, so between releases the `.md` beside one is ahead of it. Each guide carries a version stamp, `YYYYMMDD_NNN`, in the note under its title, and pandoc copies that stamp into the Word file, which also records the commit it was built from: comparing the two says whether a Word copy is current, with or without a clone beside it. `python3 tests/show_doc_versions.py` does the comparison, and `./make_docx.sh` rebuilds whichever are behind.

Editing any of them means reading [`documentation_rules.md`](documentation_rules.md) first. It is the house style, and it covers the several ways a markdown file can render correctly on GitHub and wrongly in Word.

## Running the tool

**Option A — locally in R.** You need to have R installed on your computer, along with the required R packages (listed below). Information on installing R and its packages: https://cran.r-project.org/. From the repository directory, run:

```
Rscript mlos_run_complete.R [--settings FILE] [--data FILE] [--results DIR]
```

Defaults: settings `data/OC2_settings.yaml`, data `data/OC2_data.csv`, output directory `results/` (created if missing). Defaults can also be set via the `MLOS_SETTINGS_FILE`, `MLOS_DATA_FILE`, `MLOS_OUTPUT_DIR` environment variables (plus `MLOS_LOG_FILE` / `MLOS_EXCEL_FILE` / `MLOS_JSON_FILE` for the output filenames inside the results directory). Requires the `survival` and `yaml` R packages (`jsonlite` also, for the results JSON, and `openxlsx` for the Excel export; `flexsurv` only if the optional `parametric_regression` setting is enabled).

**Option B — no local R install.** Use **[`colab_mlos.ipynb`](colab_mlos.ipynb)** in Google Colab: it installs the required packages and sets up folders for you; upload the `mlos_*.R` source files plus your data and settings files. (The notebook's instructions show the exact layout.)

Results go into a `results/` directory that is generated locally and is not tracked in this repository.  Each run starts by moving the previous run's output into `results/mLOS_<date>_<n>/`, so the results directory always holds one complete run and nothing is silently overwritten. Only files this tool generates are moved; anything else you keep there is left alone. Old run directories accumulate until you delete them.

A run produces a console log (`results/analysis_log.txt`), a full set of KM/AJ plots as PNG files, the numerical values of the curves in companion CSV files, and a JSON file (`results/results.json`) with every numerical result (except for the curve values already in the CSV files).  There is also a consolidated Excel workbook (`results/analysis_results.xlsx`) which is a rendering of that JSON. Finally, the run writes `results/data_preparation_stats.csv`, a record of how the data were transformed, removed, or kept, in the same column layout as the statistics table written by [ShelterDataPrep](https://github.com/Shelter-Data-Analysis/ShelterDataPrep) ([10.5281/zenodo.22051338](https://doi.org/10.5281/zenodo.22051338)), so the two files stack into one flow from the raw extract to the rows the statistical models ran on.

The Excel workbook can be rebuilt from the JSON file of a saved run without repeating the analysis.  Just run:

```
Rscript mlos_render.R [JSON_FILE] [EXCEL_FILE]
```

## Building a slide deck (experimental)

`mlos_review/` is a Python package that reads `results/results.json` and the figures beside it and builds a PowerPoint deck, together with a workbook of every table it made. After a normal analysis run, from the repository root:

```bash
python3 -m mlos_review.deck
```

It runs on Python 3.9 or newer and needs the packages `pyproject.toml` declares; `pip install -e .` from the repository root installs them. Installing the package itself is optional, since running from the repository root already finds `mlos_review`, but its dependencies have to be present either way. The deck builder takes its settings from `data/OC_deck_settings.yaml` and writes into `reports/`, which is created if needed and is not tracked here. It does none of the statistics: every number it shows was computed, cross-checked and written out by the R side.  The deck builder is documented in `presentation_guide.md`.

**Treat the deck as experimental, and expect that it may stay experimental.** Three separate caveats, and only the first is anywhere near settled:

- **Correctness is what is being tested.** The test suite checks that every figure on a slide is the number the analysis computed, and that the wording around it matches. That work is real, and it is also the easy half: a deck can be arithmetically faultless and still be a poor briefing.
- **Deck findings may not be consistently interesting.** Which findings reach a slide is decided by hardcoded rules against fixed thresholds, not by judgment. A run in which nothing much happened will still fill its slides, and the deck does not reliably distinguish "here is the notable thing" from "here is the largest of several unremarkable things."
- **Deck findings may omit important results.** Results researchers and practitioners care about, including ones plainly visible in the workbook and plots, might be absent from the deck. Their absence from a slide is not evidence that there is nothing there.

The workbook, the plots and the two documentation guides remain the complete record; the deck never is. Read a generated deck as raw material from which to build a briefing, not as a ready-made briefing.

## Input data format at a glance

Each CSV row in the input data file is one shelter stay, with mandatory columns `intake_date`, `outcome_date` (blank = still in care), and `outcome_type` (blank, or a code mapping to one of three canonical outcomes: **L** = community live outcome, **T** = other live outcome, **N** = non-live outcome). Optional columns: `intake_type`, `animal_group`, `animal_id`. Any further columns you include are ignored by default, but may be named in the settings file to construct an animal grouping on the fly (`animal_group_columns`) or to apply a one-off filter (`other_filter_column_name`). The settings file (YAML) defines the comparison period boundaries and outcome-code mappings; see `data/OC2_settings.yaml` for a fully-commented example. Full details are in `mlos_user_guide.md` and `mlos_math_methods.md`.

## Citing

mLOS is archived at [10.5281/zenodo.22083814](https://doi.org/10.5281/zenodo.22083814). Cite that alongside the version a run reports: the DOI resolves to the newest release, so the version is what says which one produced a result. Every run reports it, in the console log, in the `run` block of `results.json`, and on the Excel cover sheet.

[`CITATION.cff`](CITATION.cff) holds the rest, including the deposits the prepared input and the preparation tool come from, and what the shipped OC2 settings produce. Three deposits sit beside this repository:

| Deposit | DOI | Cite it when |
|---|---|---|
| Prepared input | [10.5281/zenodo.22051368](https://doi.org/10.5281/zenodo.22051368) | You ran mLOS on the shipped Orange County data. |
| OC2 results | [10.5281/zenodo.22084231](https://doi.org/10.5281/zenodo.22084231) | You used those results as they are rather than recomputing them. |
| OC2 slide deck | [10.5281/zenodo.22135419](https://doi.org/10.5281/zenodo.22135419) | The slides themselves are what you are referring to. The results deposit is the record; this is a rendering of it. |

[`PUBLISHING.md`](PUBLISHING.md) is the release runbook, and lists every citable identifier in the chain.

Issues and pull requests are welcome. Read [`documentation_rules.md`](documentation_rules.md) before editing any of the guides, and [`tests/README_TESTS.md`](tests/README_TESTS.md) before changing code that moves a number: the test suite compares against committed golden outputs, and a change that moves one is reviewed by reading that diff.
